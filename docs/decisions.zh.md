# 重大决策与原因

> 本文是 `docs/` 三份设计文档之一：[当前设计](design.zh.md)（是什么、怎么做） ｜ **重大决策与原因**（为什么） ｜
> [探索内容与复刻命令](reproduce.zh.md)（怎么跑、怎么验证、实测到什么）；
> 上游背景见 [desktop-guide.zh.md](desktop-guide.zh.md)。

| # | 决策 | 原因 |
|---|---|---|
| 1 | **放弃自研壳，改用官方 `apps/desktop`** | 自研壳跟随用户全局 Node/dsh → 环境漂移 → 插件兼容故障反复出现（实例：`DSH-better-sidebar` 依赖 `@deepseek-ai/dsh-settings` 里已被移除的 `settingsNamespace` 导出，其构建产物 `lib/index.js` 仍带这条 import，后端起不来）。官方用内置固定版本 dsh，从根上消除该问题 |
| 2 | **源仓库必须始终能解析出配置声明的 tag 并 `checkout` 到它指向的提交；上游源码不进入本仓库跟踪** | 历史完整性是唯一硬约束。**工作区状态不被保护**：构建流程先清理工作区再 checkout，上一次构建留下的改动不干扰本次构建，因此流程里不需要「还原」这个独立概念；也不为「保护源仓库整洁」发明藏文件、改名之类的机制。上游内含独立 `.git`，各机器自行 clone，tag 也得各机器自己 `fetch` 回来（决策 5）；本仓库只同步定制 |
| 3 | **三层架构：适配层 / 功能层 / patch 层** | 官方高速迭代。分层后：官方**内部实现**变 → 只改适配层（接口的拼接）；**需求**变 → 只改功能层；**接线位置**变 → 只改 patch 层。前两层是**独立文件**，构建时复制到配置指定的位置；功能层在需求不变时可长期零改动 |
| 4 | **patch 层不实现功能，只做任务调度与导出修改** | patch 只回答「在哪个位置、按什么顺序把已封装的能力接进官方流程」：它可以 import、持有接线状态、串接多个调用、按官方状态决定何时调度，但**功能本身（判断、流程、文案、回退怎么做）一律实现于功能层**。补丁失配时 `git apply` 直接拒绝，不需要额外断言机制兜底 |
| 5 | **上游版本由 `build.config.json` 的 tag 声明；构建时解析成提交，解析不到则报错退出** | 保证定制可复现地落在确定的官方版本上。**配置里存 tag 不存提交号**：升级只是换一个 tag，提交号每次现算（`git rev-parse --verify '<tag>^{commit}'`），写死提交号等于绕过 tag——下次没人知道它从哪来，tag 被重指也看不出。解析不到不允许用「当前 HEAD」凑合，也不自动 `fetch`（那会动源仓库的 ref，决策 8）：报错退出并给出取回命令 |
| 6 | **阶段 4/5 用 patch 实现，不做 dsh 插件** | 插件加载时机不对：备份/回退必须发生在 Host **启动之前**、并在 Host **启动失败时**执行，而 dsh 插件跑在 Host 进程内——Host 起不来插件就不会加载，构成循环依赖 |
| 7 | **删掉「仓库内专属 pnpm store」** | 它要求一条硬编码全局路径的「预热命令」，全局 store 一变就得手改。改为删掉上游的 store 覆盖，让 pnpm 用默认（读全局 `store-dir`）→ 位置变化自动跟随 |
| 8 | **构建产物与缓存的位置由源仓库的构建指令决定，本仓库不做重定向** | 透明原则：流程不在乎处理对象是什么。一旦为了「把产物收进本仓库」发明 junction、exclude 这类机制，流程就开始为特定场景开特例，复杂度会持续扩散。**唯一的例外是最后一步的交付搬运**（决策 41）：产物仍由上游写在原处，本仓库只在**构建成功后**按配置把它**复制**进本仓库的 `release/`，不改变任何输出路径 |
| 9 | **失败出口跟随上游；本地只在它之上加诊断** | 旧基线的错误出口是启动页 + `desktopErrorState`，当时的决策是「不弹原生框」。**`0.1.6-alpha.2` 起上游自己改成原生恢复对话框**（`fatal-recovery.ts`，按钮：退出 / 重启 / 禁用第三方插件并备份 profile patch），启动页被整体删除。本地不逆着上游重造一个窗口内的错误页：`reportFatal` 仍走上游对话框，本地只把 `startupErrorState` 的结果作为对话框的 `detail`（命中诊断用「阶段标题 + 下一步 + 原始串」，没命中就用官方原文） |
| 10 | **长任务输出必须重定向到文件** | 巨量 stdout 会灌满 agent 的 subprocess 管道并阻塞 loop（**实测卡死两次**） |
| 11 | **启动桌面端必须显式隔离 `DSH_HOME`** | 官方设计上桌面端与 CLI 共享 `$DSH_HOME`；共用真实 home 会与运行中的 agent 会话互相阻塞（**实测**）。且外层若已注入 `DSH_HOME`，dev 启动器的隔离默认值会被静默覆盖 |
| 12 | **构建脚本时间优化列入当前功能，且不得用「跳过阶段」的外部标志实现** | 见 design 的[构建脚本时间优化](design.zh.md#41-构建脚本时间优化已实施)。外部标志把「哪些不用重做」的判断权推给人，等于没解决；优化必须对处理对象透明，否则又是在流程里开特例 |
| 13 | **插件兼容性校验采用「先复制 + 安装，再校验，失败即回退」** | 校验必须在 desktop runtime 的解析语境里做；装包前不存在可信的解析根（web profile 的 `node_modules` 结论不能外推到 desktop），人为构造解析根又可能偏离真实安装结果。代价是失败点靠后，由快照回退兜底 |
| 14 | **功能判断逻辑一律放功能层，patch 里只允许「调用已封装函数」** | 层边界不能破：patch 一旦承载判断（该不该跳过、要不要回退、提示什么文案），官方每次改动都要重审策略，「官方接口变只改适配层」就退化成「官方接口变要重写逻辑」 |
| 15 | **构建缓存以「输入内容键 + 上游 pin + 产物复核」判定，宁可多算不可漏算** | mtime 不能当判据：流程每轮都 `git reset --hard` + 复制 + 打补丁，mtime 必然被刷新。命中要求 key 相同、marker 记录的产物摘要（若记了）复核通过、调用方给的 `verify` 为真；任一条不满足一律重做。**pin 由功能层混进每个键**（流程注入 `DSH_UPSTREAM_CHECKOUT`），换提交后所有缓存自动失效 —— 产物属于某个确定的官方版本，不能靠人去删目录 |
| 16 | **上游 `pnpm pack` 不是字节可复现的，缓存只承诺「复用已校验过的字节」** | 实测：同一成员连打两次，只有打包后 `dependencies` 段的键顺序不同（tar/gzip 头与文件清单一致）。所以不能拿「复用产物 == 重新打包产物」当判据，也不需要为此作废缓存 —— 复用的就是上一次已经校验通过的字节 |
| 17 | **打包并发数由本地显式传入（上限 8）** | 决策 12：判断权不推给人。**`0.1.6-alpha.2` 起上游自己实现了 `--concurrency` 的有界并发池**，本地不再自己写池：patch 只把 `package-target.ts` 调 `release:pack` 的两处补上 `--concurrency <n>`（`min(8, availableParallelism())`）。上限取 8 是因为成本是每个成员一个包管理器进程，再往上实测无收益 |
| 18 | **缓存 marker 落在源仓库自己的被忽略构建目录里** | 决策 8：不搬家、不重定向。marker 必须放在任何阶段都不会清的位置，否则它会和自己记录的产物一起消失；上游 `pnpm clean` 清空整个 `.desktop-build/` 属预期的冷缓存重置。具体位置与删除方式见 reproduce R15/R16 |
| 19 | **编译阶段的键由流程算，忽略清单必须显式声明** | 编译输入无法在功能层自证（取决于本仓库注入了什么），所以由流程按配置算键并注入（与 `npm_execpath` 同类，属环境事实）。`ignoreTargets` 只允许显式列出「不参与该指令」的注入目标（当前清单见 design 的[构建流程](design.zh.md#2-构建流程)）。**默认全部算输入**：新增的 copy/patch 只要没被声明忽略，就只会让缓存多失效一次，不会出现「输入变了却命中」。复用前跑上游 `readClientBuildRecord` 复核客户端产物 |
| 20 | **`electron-builder --dir` 复用只限本地未签名路径** | 安装包/签名/公证必须真跑。判据 = 上游各阶段 marker（它们已钉住 dsh 与 runtime 的字节，不必重新哈希 600MB）+ electron-builder 配置实体（`0.1.6-alpha.2` 起是 `apps/desktop/scripts/electron-builder-config.mjs`，`electron-builder.config.mjs` 只剩再导出）/`apps/desktop/package.json`/`pnpm-lock.yaml` + `exe`/`app.asar`/`desktop-runtime.json` 三份摘要 + 复用前跑 `afterPack` 里同一支 `verifyDesktopRuntime`。**已知残余**：Electron 自带文件树不逐字节复核（它来自 electron-builder 自己的缓存），装配中途崩溃留下的半份目录理论上可能被命中 |
| 21 | **渲染进程的适配层/功能层用经典脚本 + 全局对象组装，不用 ESM** | 这两个文件不属于网络前端的构建产物，而是由 shell 从 `dsh-app://app/local/` 自己提供、在 index 的 `<head>` 里与 boot gate 一起注入，必须早于官方 BootPage 构造就位；经典脚本没有模块上下文，两层因此各占一个同源脚本，经 `dshStartupPage` / `dshLoadingArt` 两个全局对象组装：功能层仍然只碰适配层暴露的接口（接线顺序即依赖顺序，由 patch 写死） |
| 22 | **构建时间优化只做「内容键 + 复用」，不重排上游流水线** | 否掉的三种做法：「整份产物内容寻址」只能让「什么都没改」变快，改一个文件仍全量重跑，不满足判据 ②；「在配置里把上游流水线拆成多阶段、自己编排」等于自研编排，上游改配方就静默偏离、官方新增的阶段也不会被执行；「mtime 判据 / 外部 `--skip-*` 开关」前者在本流程里必然失效（每轮 reset + 复制 + 打补丁都刷新 mtime），后者把判断权推给人（决策 12）。`prepare:runtime`（解压 Node + 拷 pnpm，≈6s）不接缓存：收益不值一层维护加一个最窄的键，且它每轮产物字节确定，不拖累下游命中 |
| 23 | **复制 web 配置只搬「配置语义」，不搬目录** | web profile 目录里混着 `.dsh-market`、`update.ps1`、`cordis.yml`、`node_modules` 这类 web 专用产物；照搬目录会把它们一起带进 desktop。因此只搬 `dependencies`/`overrides`/第三方 `dsh.profile.bundles` 与 `pnpm-workspace.yaml` 的 `allowBuilds` 段（按行合并，保留 desktop 自己的工作区设置）。`cordis.patch.yml` 不搬：它是 web profile 自己的 patch 层，可能引用 web 目录里的相对文件。web profile 不存在就直接跳过——那是默认状态，不是错误 |
| 24 | **启动失败的回退只做一次，且只在「复制成功之后」；复制成功后的任何失败都算** | 复制写下的清单要真的装出 `node_modules`（`installProfilePackages` 重建），装包失败与探针失败一样都发生在 `backend.start()` 之前，**同样必须回退**——否则 profile 会停在「清单指着一个没装的包」，之后每次启动都同样失败。快照还原 + 重建依赖两步都成功，才原地重试启动一次；第二次再失败交官方致命出口（原生对话框：退出 / 重启 / 禁用第三方插件并备份 profile patch），不自动死循环。注意上游这一版的 `reconcileBackend` 失败时默认直接 `reportFatal`，所以接线里加了「还有可回退的复制时不报告」这个守卫，否则第一次失败就会弹出模态框、把回退重试挡掉。插件探针失败属于「复制的配置不可用」，回退后按决策 28 的失败分级处理（记一次失败，连续 3 次才转 `abandoned`）。复制之前就失败的情况（例如 web 配置读不到）没有可回退的基线，也交给官方致命出口 |
| 25 | **诊断规则按阶段分组、规则互不可见，失配就退回原始错误** | 官方架构固定了运行时版本与安装路径，环境层与依赖层已消失，剩下的失败面集中在上游真实错误串上（`apps/desktop/src/*.ts`、`apps/desktop-host/src/*.ts`、`packages/boot/app-boot/src/profile.ts`）。规则空想出来的模式会误诊，所以：组间按「越窄越靠前」排序（版本一致性 → 壳与 Host 启动 → 配置 → 插件图 → 插件安装 → 包缓存），组内先命中先返回；**不设「pnpm install 失败」这类宽规则**（它会把所有包管理器失败一网打尽，让更具体的错误码规则永远轮不到）；没有命中返回 null，原生对话框照常显示官方原始串（诊断只做加法，不挡真相） |
| 26 | **web 配置迁移严格一次性，窗口由 profile 内的记账文件判定** | 迁移的目标是「把 web 上装好的插件带进来一次」，不是「让 desktop 镜像 web」。每轮对账会让 web 侧的临时改动静默改写 desktop，也会在 desktop 已被用户接管后覆盖用户装的插件。因此只在 desktop profile 还是官方空形态、且没有写下了结记账时迁移；判据用 profile 内的 `.dsh-web-migration.json`（`done`/`abandoned`/`retry`）而不是「profile 是否存在」——它同时覆盖「官方重置后重新迁移」（文件随 profile 消失）与「失败后重试」（`retry` 未了结）。web 之后新增的插件不自动迁移，要用就在应用内装 |
| 27 | **迁移的依赖 spec 照搬，不再需要放宽版本校验** | 真实 web profile 的依赖是 range（`^`）与 `github:`（实测 11 个插件：5 个 git、5 个 range、1 个精确）。旧基线里官方 desktop profile 只接受精确版本，当时靠 patch 放宽 `projectManifest` 的校验；**`0.1.6-alpha.2` 起官方 profile 清单只做「是个 JSON 对象」这一层校验，精确版本约束不存在了**，该 patch 随之删除。代价不变：非精确 spec 的解析结果由 pnpm 决定，不保证与 web 侧装到的一致 |
| 28 | **迁移失败按性质分级：临时性重试、确定性放弃，重试有上限** | 装包/探针失败多为临时性（网络、store 锁），一律放弃会让一次抖动永久失去迁移机会；Host boot 失败是确定性的（插件等 desktop 不提供的服务，实测 `dsh-whale-widget`），一律重试会让用户每次启动都失败一次。因此：装包/探针失败 → 回退、不写下了结记账、下次重试，**连续 3 次**转 `abandoned`；Host boot 失败 → 回退、重试一次后记 `abandoned` |
| 29 | **加载动画不依赖内容嗅探** | 旧基线上 PNG 以 `application/octet-stream` 返回，能显示只因为 Chromium 对 `<img>` 做内容嗅探、且上游没加 `nosniff`——上游一加就破，而且从代码里看不出这层依赖，当时的对策是 patch 官方 MIME 表加 `.png: 'image/png'`。**`0.1.6-alpha.2` 起官方的文档服务自己就把 `.png` 映射成 `image/png`**，本地那条 MIME patch 随之删除；动画资源改走本地新增的 `/local/` 分支，同一个 MIME 表 |
| 30 | **诊断新增「插件安装失败」阶段** | 装包失败原先落进「包管理缓存失败」，会把用户往「磁盘/缓存坏了」的方向带，实际是「这个包装不上」。新增独立阶段收 `ERR_PNPM_FETCH_`（实测样本 `ERR_PNPM_FETCH_404`），排在插件图之后、包缓存之前，避免被宽模式截胡 |
| 31 | **上游删掉的载体不硬凑：能重挂就重挂，上游已经接管就退场** | 跳到 `0.1.6-alpha.2` 时上游删掉了 `renderer/startup.html`（启动等待改由网络前端 BootPage 承担）、删掉了 `checkFsExt`（`fs-ext` 早已被 `node-addon-system` 取代）、删掉了桌面插件窗口、也让 profile 清单不再校验精确版本。逐项判定：① 加载动画**重挂**到官方 BootPage（适配层跟随 `data-dsh-boot` / `data-dsh-boot-spinner`，功能层只管「还在加载就展示」）；② 启动失败诊断**重挂**到官方原生恢复对话框的 `detail`；③ fs-ext 容忍层、桌面插件窗口相关的文案、精确版本 patch **退场**（没有可容忍的检查、没有那个窗口、没有那条校验）。判据是「这段定制还有没有一个真实载体」——为了保住旧实现而在上游重新发明一个载体，违反最小改动 |
| 32 | **profile 的包操作放在适配层，因为官方把这条路搬进了 Host** | `0.1.6-alpha.2` 的 Electron 主进程里已经没有 pnpm 能力（`DesktopProjectManager` 只剩 `disableAllPlugins` / `applyRelease`，profile 包操作随 Host 走）。迁移与回退都需要「按清单重建 profile 依赖」，而这个动作必须发生在 Host 启动之前，只能由主进程做。**这是「官方内部实现变动」，由适配层吸收**：`src/adaptator/profile-packages.mjs` 的 `installProfilePackages` 与官方 Host 走同一条路（Electron 以 `ELECTRON_RUN_AS_NODE` 跑内置 pnpm、`--ignore-scripts`、非 frozen），镜像地址读 `DSH_LOCAL_NPM_REGISTRY`。**功能层的需求（④ 重建依赖）没有变，所以功能层不碰这件事**：patch 把适配层的函数作为 `onRepair` 喂给 `rollbackProfile`。profile 目录的建立仍复用官方 `createPluginProfile`（patch 只加一个 `ensureProfileDirectory` 出口） |
| 33 | **分层规范做成会红的门限，而不是文档里的约定** | 腐败（功能层吃官方内部实现、patch 里长功能逻辑）**不会让任何测试失败**，只会让下次上游升级从「重新生成 patch」变成「重写两层」——`0.1.6-alpha.2` 那次移植就是实例：旧诊断规则表 14 条里 9 条绑定的错误串在新版源码里实测 `hits=0`，静默失效。判据只取**可机械判定**的（依赖方向、官方字面量/正则的集合运算、中文字面量、进程调用、阈值、copy 登记、target 存在），规则表与 id 见 design §4.3 |
